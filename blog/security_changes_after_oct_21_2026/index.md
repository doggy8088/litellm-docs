2026 年 10 月 21 日，我們自己的發布管線建置、簽署並發布了惡意的 `litellm==1.107.0`。我們已在 10 月 23 日發布了[根本原因分析](/blog/security-incident-oct-21-2026-attack-chain)。

本文將逐一說明我們學到了什麼，以及我們將如何防止此事再次發生。這包括：為何我們在 3 月事件後所做的強化未能防止這次事件、10 月實際上哪裡出了問題，以及我們已經改變了什麼、承諾要改變什麼。

## 截然不同的攻擊 {#very-different-attacks}

從外表看，3 月與 10 月很相似：透過我們自己的管道發布了惡意的 LiteLLM 套件。然而，這兩次攻擊發生在兩個截然不同的表面上，這就是為何我們在 3 月之後建立的管控措施未能防止 10 月事件的原因。

**3 月是一次供應鏈攻擊。** 一個遭到入侵的第三方相依套件（Trivy，在我們的 CI 安全掃描中以未釘選版本使用）在我們的 CI 內執行。它讀取了我們保存在環境變數中的靜態 PyPI、GHCR 與 Docker 發布憑證，並用它們來發布惡意套件。攻擊者從未取得我們 GitHub 組織的存取權。他們控制了一個建置步驟，而該步驟握有我們的金鑰。

![CI/CD v2 架構：BerriAI/litellm 在隔離環境中執行安全掃描與單元測試，手動觸發的發布從私有的 BerriAI/project-releaser 儲存庫執行，CircleCI 在 main 與 litellm_ pull request 上執行 E2E 測試](/img/blog/security_changes_after_oct_21_2026/ci_cd_v2_architecture.png)

我們重建了管線以因應此事。[CI/CD v2](/blog/ci-cd-v2-improvements) 將每個階段隔離，將驗證與發布拆分到不同的儲存庫，以 Trusted Publishing 取代靜態 PyPI 憑證，以 cosign 簽署容器映像，讓發布標籤不可變，釘選每個 GitHub Action，並在每個 pull request 上導入自動化掃描。我們的目標是讓不受信任的程式碼與長效憑證遠離發布路徑。

**10 月是一次基礎設施入侵。** 沒有任何相依套件遭到入侵，攻擊者也不是透過 CI 進入。攻擊始於一個內部實驗性服務的管理 API 金鑰，該金鑰在 5 月被不慎提交到一個公開儲存庫。該服務又握有我們兩位組織擁有者之一的 GitHub CLI OAuth 權杖。有了該權杖，攻擊者就是一位組織擁有者。

![10 月攻擊鏈：一個被刪除的 commit 暴露了 LiteLLM Agent Platform 主金鑰，其 GitHub 權杖讓攻擊者能執行工作流程以竊取其他 PAT，攻擊者將 project_releaser 指向一個被投毒的 fork，惡意版本隨後被發布到 GHCR、Docker 與 PyPI](/img/blog/security_changes_after_oct_21_2026/october_attack_chain.png)

組織擁有者有能力變更 GitHub 組織中幾乎任何東西，包括管線程式碼、分支保護、必要檢查，以及誰核准什麼的規定。攻擊者將變更推送到我們的私有發布儲存庫，使管線從他們的 fork 而非 `BerriAI/litellm` 拉取原始碼，以擁有者權杖將其推過分支保護，派發了管線，並以第二個被竊的權杖核准了生產閘門。我們的管線在其他方面未作變更，它建置了該 fork，以我們的 cosign 金鑰簽署映像，並以我們的 Trusted Publisher 身分發布了一切。

| | March 2026 | October 2026 |
| --- | --- | --- |
| 進入點 | 在 CI 中執行的遭入侵相依套件 | 內部實驗性服務的外洩 API 金鑰 |
| 攻擊者握有什麼 | 來自 CI 環境變數的靜態發布憑證 | 一位組織擁有者的 GitHub 權杖，以及隨後透過一次性工作流程竊取的其他權杖 |
| 管線做了什麼 | 什麼都沒做；攻擊者直接以竊得的金鑰發布 | 透過正常路徑建置、簽署並發布攻擊者控制的原始碼 |
| 產出物看起來如何 | 未簽署，在管線之外發布 | 有效簽署，具備有效的 Trusted Publishing 來源證明 |
| 3 月的管控措施做了什麼 | 因應此事而建立 | 如設計般運作，並顯著減輕了影響（例如既有的發布標籤無法被覆寫）。但無法完全防止這次攻擊。 |

**我們在 3 月事件後導入的管控措施，在防禦供應鏈攻擊方面是有效的。** Trusted Publishing 與簽署證明產出物來自我們的管線。10 月事件並不否定這一點：v1.107.0 確實來自我們的管線；當攻擊者是組織擁有者時，沒有任何管線管控能防禦，因為擁有者擁有這條管線。

## 我們正在改變什麼 {#what-were-changing}

您可以在[這裡](/blog/security-incident-oct-21-2026-attack-chain)找到我們對此事件根本原因的分析。我們為解決導致此事件的主要因素而採取的行動橫跨數個類別。

### 身分與權限 {#identity-and-privilege}

**沒有任何人類的日常帳號是擁有者。** 我們的 GitHub 企業與發布核准閘門由單一專用帳號持有，該帳號只與我們辦公室的一台特定裝置關聯。執行發布需要該帳號。用於營運工作的組織所有權將由專用擁有者帳號執行，與人們用來撰寫程式碼的帳號分開。任何擁有者帳號都不得授權 OAuth 應用程式，或透過 API 或 `gh` CLI 使用，且擁有者帳號的任何以權杖為基礎的活動都會引發警示。

**一般使用者可以使用代理程式。一般使用者永遠不能是擁有者或管理員。** 我們不會要求工程師停止使用 Claude Code 與類似工具。相反地，我們依風險調整帳號的規模。開發者機器上的一切都應假設可被其上執行的代理程式讀取，因此一般使用者機器上的代理程式只能做一般使用者能做的事，不能更多。同樣的規則也適用於 Google Workspace：管理角色移至專用管理員帳號，與日常使用分開。

**內部建置位於身分感知代理之後。** 我們的實驗性服務建置速度快，經常使用大量代理程式參與的工作流程。這些系統不應暴露在網際網路上。所有內部部署現在都位於身分感知代理之後。

**全面採用抗網路釣魚的認證。** 要求抗網路釣魚 MFA 的 Okta SSO 已在我們的 GitHub 組織中強制執行。我們正將其擴展至所有內部系統以及使用者佈建與取消佈建，讓存取權在單一位置授予與移除。

### 憑證 {#credentials}

**每個儲存庫都啟用秘密掃描與推送保護。** 這適用於 `BerriAI` 組織以及 `LiteLLM-Labs`，也就是我們放置實驗性專案的組織。

**以工單追蹤金鑰撤銷。** 在 5 月外洩、並隨後導致 10 月 10 日最初入侵的那把金鑰並未被撤銷。秘密掃描必須自動開啟工單，且工單只有在撤銷獲得確認時才能關閉。

**自動化永遠不以個人身分認證。** 自動化將以 GitHub App 或具最小權限範圍、會到期的細粒度權杖進行認證，並透過定期權杖稽核強制執行。此外，GitHub CLI OAuth 權杖永遠不得在其預期範圍之外使用：也就是在開發者的機器上授權 GitHub CLI。

**秘密僅在受保護的分支上可用。** 儲存庫層級的秘密正移入具有部署分支政策的 GitHub 環境中，因此只有受保護分支上的工作流程能讀取它們。雖然這無法阻止那次發布，但在非擁有者權杖被竊的威脅模型下，它能阻止其他權杖被竊取外洩。

### 偵測與回應 {#detection-and-response}

**更深入投資監控與警示。** 我們組織的 GitHub 稽核記錄現在會串流至 Splunk，且警示已就位。現在已有警示會在威脅行為者在 GitHub 中採取的所有行動上觸發。更多警示正在開發中，將在威脅行為者未特別利用的政策違規與覆寫上觸發，以及異常偵測，例如意外的地理來源與不可能的移動。

**出貨後的自動發布驗證。** 一個在 GitHub 之外執行的驗證器將下載每個已發布的 wheel、sdist 與映像，從 `BerriAI/litellm` 簽出對應的標籤，並比較內容。一旦有任何差異，它會警示人類並自動撤下這些發布。

**擴大我們的安全團隊。** 我們正在尋找優秀的安全工程師，協助我們維護社群的安全。如果您有興趣，請在[這裡](https://jobs.ashbyhq.com/litellm/93705fde-0daa-49ce-94be-4551d3ac662d)申請。

### 更廣泛的計畫 {#the-broader-program}

以下事項都與我們剛經歷的事件無關，但都是我們即將採取（在某些情況下已經開始）的行動，以改善我們的整體安全態勢。

- **Chainguard Libraries for Python 與 Chainguard Catalog**，從經過強化、持續重建的供應鏈取得我們的相依套件並建置映像。這是針對 3 月類別攻擊（遭入侵的上游相依套件）的防禦，不是針對 10 月類別。
- **改善 LiteLLM 的弱點態勢**，透過與 HackerOne 合作進行受管理的弱點揭露計畫與第一線分流，並與 Trail of Bits 合作強化應用程式碼本身。
- **LiteLLM Private Registry**，已於 [10 月 27 日宣布](/blog/litellm-private-registry)，將用於在公開發布之前交付最嚴重弱點的修復。請注意，此註冊表的目的專門在於分發受禁運的弱點修復，就發布而言並不構成實質的安全邊界。
- **符合 FIPS 140-3 的映像**將在不久的將來提供給需要 FIPS 驗證密碼學運算的客戶。
