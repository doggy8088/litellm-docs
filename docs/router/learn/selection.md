# 如何挑選一個部署 {#how-a-deployment-is-picked}

{/* keep-version-note */}

一次挑選會將所請求的名稱轉換為一個部署。它在每一次嘗試內部執行，因此重試會再次挑選，並可能落在別的
地方。`router.select()` 執行相同的挑選，但不呼叫提供者。

## 篩選器鏈 {#the-filter-chain}

解析產生候選，而一連串篩選器會移除目前不得服務這個請求的候選。篩選器只能移除候選。鏈尾的策略看到的是
剩下的東西。

![從前置路由與名稱解析開始，經過每個篩選器，到策略，或到沒有可用部署錯誤的篩選器鏈](../img/selection-1.svg)

## 各個篩選器 {#the-filters}

**路由能力篩選器。** 只有某些提供者能服務的呼叫，會略過其提供者無法服務它的部署，只要還有另一個候選
留著。例如，對一個同時有 OpenAI 部署與 Anthropic 部署的群組發出的 `/v1/decisions` 呼叫，會略過
Anthropic 那個，因為 litellm 沒有該提供者的 Decisions 設定。

**健康檢查篩選器。** 在 `enable_health_check_routing` 之下，背景健康檢查的結果也算數。被上一次檢查
標記為不健康的部署會被移除，只要該結果比 `health_check_staleness_threshold` 新。
`background_health_check_model_groups` 將此限制在某些模型群組。如果這個篩選器會使候選歸零，它會
改為保留每一個候選，因此故障的健康檢查器不會讓整個群組倒下。

**冷卻篩選器。** 移除路由快取中每一個帶有有效 `deployment:{id}:cooldown` 鍵的部署。冷卻是某個請求
上的失敗保護後續請求的方式，見[重試、備援與冷卻](reliability.md)。當健康檢查搭配
`allowed_fails_policy` 驅動路由、且冷卻篩選器會使候選歸零時，router 會為該請求忽略冷卻。

**封鎖篩選器。** 移除帶有 `model_info.blocked` 的部署，管理員設定它來暫停一個部署而不刪除它。如果
一個群組的每個部署都被封鎖，錯誤會如此說明。

**回呼篩選器。** 回呼也能縮小候選範圍，而且它們像任何其他篩選器一樣在鏈中執行。預算限制器會移除其
提供者已超出其 `provider_budget_config` 預算的部署。部署與工作階段親和性會將對話保持在先前服務它的
部署上，做法是只要先前的部署是健康的，就將其他全部部署從考慮中移除。

**呼叫前檢查。** 在 `enable_pre_call_checks` 之下，router 會移除 prompt 超出其上下文視窗的部署、
位於請求的 `allowed_model_region` 之外的部署，以及無法接受所請求參數的部署。prompt 的 token 計數
與每個部署的限制來自模型成本對照表。當什麼都不剩時，錯誤會說明是哪個檢查移除了最後一個部署。例如，
上下文視窗錯誤是備援遍歷可以路由到 `context_window_fallbacks` 的錯誤。

**標籤篩選器。** 在 `enable_tag_filtering` 之下，請求的標籤只保留其 `litellm_params.tags` 包含
它們的部署。標記為 `default` 的部署服務沒有標籤的請求。`!tag` 會排除帶有該標籤的部署，而 `&tag`
則要求帶有它。

**路由外掛候選。** 當路由外掛在前置路由期間執行過時，只會留下它們所留下的模型的部署。

**純文字篩選器。** 帶有圖片的請求會略過未宣告視覺支援的部署，只要還有另一個候選留著。

**順序篩選器。** 只保留其餘部署中 `litellm_params.order` 最低的那些，或順序備援所針對的順序的那些。
見下方。

**被排除與重試略過的 id。** 重試會略過已經為這個請求失敗過的部署，但僅限還有其他東西留著的時候。
加權容錯移轉會直接排除 id，而被排除的 id 永遠不會被挑選到。

## 以 `order` 表示的優先順序 {#priority-with-order}

`order` 是群組內優先順序的運作方式。帶有 `order: 1` 的部署會在它們之中任何一個通過篩選器時，承接
所有流量。帶有 `order: 2` 的部署，只有在備援遍歷以該順序針對該群組、且在每個 `order: 1` 部署都為
該請求失敗之後，才會看到流量（見[重試、備援與冷卻](reliability.md)）。混用有順序與沒有順序的部署很
容易出錯。當任何候選設定了順序時，這個篩選器會移除沒有順序的部署，而順序備援也永遠不會以它為目標。
因此，要給群組的每個部署都設定順序，或一個都不要設定。優先順序路由群組會將每個成員的優先順序作為其
部署的 `order` 來提供，因此同一個篩選器會遍歷這些優先順序（見[策略、路由群組與子路由器](strategies.md)）。

![以 order 表示的優先順序：一般挑選去到兩個 order 1 部署，而 order 2 部署只有在 order 1 失敗之後才會得到請求](../img/selection-2.svg)

## 捷徑 {#shortcuts}

依其 id 解析為單一部署的名稱，即使該部署正在冷卻也會被服務。回呼篩選器與策略會被略過，因為沒有什麼
可選的。自訂策略會略過整條鏈，見[策略、路由群組與子路由器](strategies.md)。

## 當什麼都不剩時 {#when-nothing-is-left}

挑選會以「No deployments available for selected model」失敗。錯誤會列出處於冷卻中的部署以及距離最快
結束的冷卻還剩的秒數，並說明呼叫前檢查是否開啟，因為它們是常見的原因。備援遍歷將這個錯誤視為速率限制
一樣處理，因此每個部署都在冷卻的群組會備援到它的備援群組。
